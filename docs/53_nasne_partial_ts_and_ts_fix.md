# 53. 救出 TS の形式 (ARIB 部分 TS) と変換ツール ts_fix.py

## 0. 要約

- **rescue.py が保存する TS の形式 (確定)**: rescue.py は、nasne が DTCP-IP で送り出したバイト列 (pydtcpip `stream` の出力) をそのまま保存する。これは録画機が保存する形式である **ARIB の部分 TS** (partial TS) で、パケットは 192 バイト (4 バイトのタイムスタンプ + 188 バイト)、番組情報は SIT (PID 0x1F) にだけ入っており、放送の TS にある NIT / SDT / EIT / TOT が無い。
- **一般のツールでの扱い**: このため、チャンネル名・番組名・放送日時・ジャンルなどを SDT / EIT / TOT から読むツールでは、番組情報を取得できない (再生はできる)。
- **対処 (実装・検証済み)**: [tools/dtcpip-rescue/ts_fix.py](../tools/dtcpip-rescue/ts_fix.py) を追加した。SIT の内容から NIT / SDT / EIT[p/f] / TOT を合成し、188 バイトの一般的な TS に変換する。映像・音声・字幕・データ放送のパケットには触れない。
- **検証**: 3倍・DR の両方の録画を変換し、全パケット走査で不良が無いことを確認した。ARIB の文字列を読める外部ライブラリ (ariblib) で、合成した SDT のサービス名と EIT の番組名・時刻を読み出せることも確認した。取り直した録画を変換すると、先に変換したものとバイト単位で一致し、変換済みファイルを再変換しても同じバイト列になる (§6)。
- **未確定・制限**: EIT の「次の番組」(following) は空になる (SIT に情報が無い)。EIT[schedule] は合成しない。録画開始直後の数秒は、前の番組が「現在の番組」として出ることがある (§5)。

## 1. 位置づけと範囲

- [docs/49](49_dtcpip_rescue_tool_and_windows.md)・[docs/50](50_dtcpip_rescue_tool_internals.md) で正式化した救出ツールの、取得物の **形式** についての記録である。救出の経路 (AKE・復号・転送) には変更を加えない。
- 本リポジトリの範囲 (AGENTS.md §6) との関係: 対象は DTCP-IP で取り出した映像そのものの形式であり、救出物を一般のツールで扱えるようにするための後処理なので、救出ツールの一部として置いた。
- 鍵・資格情報には一切触れない。変換ツールは救出済みの TS ファイルだけを入力にとる。

## 2. 観測した事実 (変換前の TS)

### 2.1 転送形式の申告

- 列挙で得た録画の原本 res の protocolInfo は、全件 `application/x-dtcp1;...;CONTENTFORMAT="video/vnd.dlna.mpeg-tts"` だった。`mpeg-tts` は DLNA でタイムスタンプ付き TS (192 バイトパケット) を表す。
- 原本 res のプロファイルは、3倍録画が `DTCP_AVC_TS_JP_AAC_T` (AVC)、DR 録画が `DTCP_MPEG_TS_JP_T` (MPEG-2 のまま)。どちらも末尾 `_T` (タイムスタンプ付き) で、以下の構造は録画モードによらず同じだった (§2.2)。

### 2.2 パケットと PSI/SI の構成

救出した TS をパケット単位で数えた結果。3倍録画・DR 録画のどちらでも、表の種類と PID の割り当ては同じだった:

| 項目 | 観測値 |
|---|---|
| パケット長 | 192 バイト (先頭 4 バイトがタイムスタンプ、+4 バイト目が同期バイト 0x47) |
| PAT (PID 0x0000) | あり。program_number 0 (ネットワーク PID) の行が **PID 0x001F** を指す |
| SIT (PID 0x001F、table_id 0x7F) | あり (約 1 秒間隔) |
| DIT (PID 0x001E、table_id 0x7E) | あり (不連続点を示す表。調べた録画ではいずれも先頭付近に 1 回だけ) |
| NIT / SDT / EIT / TOT (PID 0x0010 / 0x0011 / 0x0012 / 0x0014) | **パケット 0 件** |
| PMT・映像・音声・字幕・データ放送の PID | 放送どおり |

これは ARIB STD-B21 (受信機の機能仕様) と TR-B14 (運用規定) が定める **部分 TS** の形である。部分 TS は、受信機が TS から 1 サービスを取り出して記録・出力するときの形式で、放送の SI (NIT / SDT / EIT / TOT 等) を落とし、そのサービスに必要な情報だけを SIT にまとめる。不連続点は DIT で示す。

### 2.3 SIT の中身

SIT は「伝送情報ループ」と「サービスループ」からなる。観測した記述子:

| 位置 | タグ | 記述子 | 入っている情報 |
|---|---|---|---|
| 伝送情報 | 0x63 | partial_transport_stream | 部分 TS の最大ビットレート等 |
| 伝送情報 | 0xC2 | network_identification | 国コード "JPN"、メディア種別 ("TB" = 地上波など)、**network_id** |
| 伝送情報 | 0xCD | TS_information | リモコンキー ID、**TS 名** (ARIB 8 単位符号の文字列) |
| サービス | 0x48 | service | サービス種別、事業者名、**サービス名** |
| サービス | 0x4D / 0x4E | short_event / extended_event | **番組名・番組概要**、詳細 (番組内容・出演者等) |
| サービス | 0x54 | content | **ジャンル** |
| サービス | 0x50 / 0xC4 / 0xC7 | component / audio_component / data_content | 映像・音声・データ放送の構成 |
| サービス | 0xD6 | event_group | **event_id** (自サービスの service_id と組になった行) |
| サービス | 0xC3 | partialTS_time | **番組の開始時刻・長さ**、JST_time_flag が立っていれば **現在時刻 (JST)** |

- partialTS_time の現在時刻は、毎回の SIT に入るわけではない。観測では SIT 5 回に 1 回程度だった。
- 番組の境目では、SIT のサービスループの番組情報 (event_group の event_id、partialTS_time の開始時刻、short_event の番組名) が次の番組に切り替わる。録画の先頭付近では前の番組の情報が入っていることがある (§5)。

### 2.4 番組情報が読めない理由 (解釈)

- 一般の TS ツールは、チャンネル名を SDT、番組名・時刻・ジャンルを EIT、現在時刻を TOT から読む。部分 TS にはそれらが無いため「情報なし」になる。SIT を解釈するツールは少ない。
- 192 バイトパケットのため、188 バイトを前提にするツールでは TS として開けないこともある。
- 情報そのものは SIT に全部残っているので、**表を作り直せば元の放送と同等の番組情報になる** と判断した (§3)。

## 3. 変換の設計 (ts_fix.py)

### 3.1 方針

- 入力の SIT から、放送の形の NIT / SDT / EIT[p/f] / TOT を合成して差し込む。**記述子は SIT のものをバイト単位でそのまま使う**。ARIB 8 単位符号の文字列も再符号化しないので、文字化けや情報の欠落が起きない。
- 映像・音声・字幕・データ放送・PMT のパケットは一切変えない。SIT と DIT も残す (部分 TS を解釈するツールのため)。
- 標準ライブラリだけで書き、救出ツールと同じく Python 3.10+ で動く。

### 3.2 処理の流れ

1. **パケット長の判定**: 先頭 10 パケットの同期バイトで 192 / 188 を判定する。192 なら先頭 4 バイトのタイムスタンプを捨てる。
2. **PAT の書き換え**: program_number 0 の行を PID 0x001F (SIT) から **0x0010 (NIT)** に変え、CRC を再計算する。transport_stream_id は PAT の値を使う。
3. **既存の 0x0010 / 0x0011 / 0x0012 / 0x0014 は捨てる**: 合成した表と元の表が混ざらないようにする。これにより変換済みファイルを再変換しても同じ結果になる。
4. **SIT の解析**: SIT のセクションを組み立て、CRC が合うものだけを使う。内容が変わったときだけ表を作り直す。
5. **表の合成と差し込み**: PAT の直後に、PCR で測った間隔で各表を差し込む。

| 表 | PID / table_id | 間隔 | 中身 |
|---|---|---|---|
| NIT (自ネットワーク) | 0x0010 / 0x40 | 10 秒 | network_name 記述子 (TS 名)、TS ループに TS_information 記述子 (SIT のもの) と service_list 記述子 |
| SDT (自ストリーム) | 0x0011 / 0x42 | 2 秒 | サービスごとに service 記述子 (SIT のもの)。EIT_present_following_flag = 1、running_status = 4 (放送中) |
| EIT[p/f] (自ストリーム) | 0x0012 / 0x4E | 1 秒 | section 0 = 現在の番組 (event_id、開始時刻、長さ、SIT の番組系記述子)。section 1 = 次の番組 (空) |
| TOT | 0x0014 / 0x73 | 5 秒 | SIT の JST_time を基準に PCR の経過で進めた現在時刻。local_time_offset 記述子 (JPN、オフセット 0) |

- **識別子**: original_network_id は SIT の network_identification 記述子の network_id、transport_stream_id は PAT の値。
- **版番号**: サービス構成が変わったら NIT / SDT の version を、番組が変わったら EIT の version を 1 つ進める (5 ビットで巡回)。
- **時刻**: SIT に JST_time が来るたびに、その時点の PCR と組にして基準を取り直す。PCR の 33 ビットの巡回も考慮する。
- **パケット化**: pointer_field 0 で始め、余りは 0xFF で埋める。連続性カウンタは PID ごとに数える。
- **書き出し**: `<出力名>.partial` に書き、完了したら出力名へリネームする。入力は変更しない。

### 3.3 採らなかった方法と理由

- **SIT だけを残して 188 バイトに切り詰める**: パケット長の問題は解けるが、SDT / EIT を読むツールからは引き続き情報が見えないので不採用。
- **SIT を捨てる**: 部分 TS を解釈するツール (録画機の取り込み機能など) のために残した。PAT の参照先は NIT に変えたが、SIT のパケットは PID 0x001F のまま流れている。
- **EIT[schedule] の合成**: SIT にあるのは現在の番組だけで、番組表を作る材料が無いので作らない。
- **救出ツール本体 (rescue.py) への組み込み**: manifest と SHA-256 は「nasne から受け取ったバイト列」を記録するもので、変換版を混ぜると検証の意味が変わる。救出と変換は別の手順として分け、変換は利用者が必要に応じて行う形にした。

## 4. 使い方

使い方は [ツール README](../tools/dtcpip-rescue/README.md) の「番組情報の補完」節に書いた。要点だけ:

```bash
python3 ts_fix.py out/*.ts            # out/fixed/ に書き出す
python3 ts_fix.py out/*.ts -o <出力先>
```

- 出力先に同名ファイルがあればスキップ (`--overwrite` で上書き)。
- manifest・`.ts.json`・`SHA256SUMS.txt` の SHA-256 は変換前のファイルの値で、変換版とは一致しない。

## 5. 既知の制限と注意

- **EIT の following は空**: SIT に次の番組の情報が無いため。「次の番組」を表示するツールでは空欄になる。
- **録画先頭の番組情報**: 録画開始直後の数秒は、SIT が前の番組を現在の番組として示していることがあり、EIT もそれに従う。放送をそのまま録画した TS と同じ振る舞いで、変換の誤りではない。番組名を 1 つだけ取り出すツールでは、前の番組名が出ることがある (例: 番組が切り替わる直前から録画が始まった場合)。
- **ハッシュ**: 変換版は救出時の SHA-256 と一致しない (§3.3)。

## 6. 検証

検証はすべて nasne (CUHJ-15004) から救出した録画で行った。

### 6.1 構造の検査 (全パケット走査)

変換した各ファイルを先頭から最後まで読み、次をすべて満たすことを確認した。

- ファイルサイズが 188 の倍数で、全パケットの先頭が 0x47。
- PAT の program_number 0 が PID 0x0010 を指す。
- PAT / NIT / SDT / EIT / TOT の全セクションの CRC32 が正しい。
- 合成した PID の連続性カウンタに抜け・重複が無い。
- PAT / NIT / SDT / EIT / TOT のすべてが 1 回以上現れる。

対象は 3倍・DR の両方を含む、地上波と BS の複数のサービスの録画で、**不良は無かった**。

### 6.2 ARIB の文字列としての読み出し

- ARIB の SI を解釈する外部ライブラリ ariblib (別環境に導入、本リポジトリには含めない) で、合成した SDT・EIT・TOT を読んだ。§6.1 の全件で、SDT からサービス名、EIT から番組名・開始時刻・長さが読めた。
- 番組名を録画一覧 (DLNA の DIDL) のタイトルと照合した (全角・半角をそろえ、記号と `[字]` 等の付記を除いて比較)。違いがあったのは、EIT 側にある記号 (㊙ など) が一覧のタイトルに無い場合だけだった。
- 全件で、TOT の時刻の範囲は EIT の番組の放送時間帯 (最初の番組の開始から最後の番組の終了まで) に収まっていた。
- 番組をまたぐ録画 (前の番組の終わりから始まり、次の番組の頭まで入っているもの) では、EIT の版番号が進むたびに現在の番組が前 → 目的 → 次と切り替わることを確認した。

### 6.3 動作確認

§6.1 で検査した録画から 3倍・DR の両方を救出ツールで取り直し (変換前の 192 バイト TS)、`ts_fix.py` で変換した。

| 試験 | 結果 |
|---|---|
| §6.1 で検査した変換版との比較 | すべてバイト単位で一致 (同じ入力からは同じ出力になる) |
| 変換版 (188 バイト) をもう一度変換した結果との比較 | すべてバイト単位で一致 (再変換で内容が変わらない) |
| §6.1 の構造の検査・§6.2 の読み出し | すべて合格 |

試験に使った録画には、前後の番組をまたぐもの (§6.2) を含めた。

### 6.4 処理時間

- 1〜2 GB の録画で 1 件 5〜10 秒程度 (約 0.2 GB/秒) だった。入力をすべて読んで書き直すだけなので、速度はほぼディスクの読み書きで決まる。

## 7. 残件・未確定事項

- 救出物が部分 TS であることは、nasne が保存している形式をそのまま送り出しているものと解釈しているが、本体の内部での保存形式との対応は本書では確かめていない (解釈)。
- BS は一部のサービスでのみ確認した。CS (110 度) の録画は未検証。
