## 0. 要約

- **PR #2** (投稿者 **hydh**、2026-11-19、head `ff93813`、+626/−0、4 ファイル): 救出した TS (ARIB 部分 TS) を、番組情報 (局名・番組名・放送日時) を一般のツールから読める一般的な TS に変換する後処理ツール `tools/dtcpip-rescue/ts_fix.py` の追加。救出経路 (rescue.py / GUI) と資格情報の扱いには変更なし。
- **静的レビューの結論**: 阻害要因なし。純粋な追加で、入力ファイルを変更せず、標準ライブラリのみ、資格情報・鍵には一切触れない。細部の指摘は §3.3 のとおりいずれも軽微 (任意の 188 バイト TS を入れた場合の静かな表消失など、想定入力の範囲外の話が中心)。
- **実データ検証 (本書 §5)**: こちらで保持していた実救出サンプル (3倍・DR、地上波) で変換を実行し、独自の検証スクリプトで構造・CRC・連続性・保持パケットのバイト同一性・冪等性・決定性をすべて確認した。ffprobe でも変換版からのみ service_name が読めた。実機へのアクセスは不要だったため行っておらず、コピーの消費もない。
- **統合方針 (本書 §6)**: 本人の方針「救出ツールで従来方式と PR #2 の方式を選べるようにする」に対し、(1) PR #2 はそのまま取り込み、(2) 選択の配線 (CLI の `--fix` / GUI のチェックボックス、既定はオフ) は後続の変更としてこちらで用意する、の 2 段階を提案する。マージ判断は本人が行う (本書は判断材料まで)。

方式の位置づけ: これは新しい「救出方式」ではなく、**救出済みファイルへの後処理**である。rescue.py が保存する TS は nasne が DTCP-IP で送る ARIB 部分 TS (192 バイトパケット、番組情報は SIT のみ) であり、再生はできても SDT / EIT / TOT を読むツールからは番組情報が見えない。ts_fix.py は SIT から表を合成してこの欠落を埋める。

## 2. 変換の仕組み (ts_fix.py)

1. 先頭パケットの同期バイト位置で 192 / 188 バイトを判定。192 なら TTS ヘッダ 4 バイトを落とす。
2. PAT の program_number 0 (ネットワーク PID) を SIT (0x1F) から NIT (0x10) に書き換え、CRC を再計算する (PAT はキャッシュされ、同一内容の再書き換えは冪等)。
3. PID 0x10 / 0x11 / 0x12 / 0x14 の既存パケットは捨てる (合成表との混在防止。変換済みファイルの再変換が同じ結果になる理由でもある)。
4. SIT セクションを組み立て、CRC が一致するものだけを解析する。伝送情報ループ (network_identification → network_id、TS_information → TS 名) とサービスループ (service / short_event / extended_event / content / event_group → event_id / partialTS_time → 開始時刻・長さ・JST_time) を取る。
5. 表を合成し、PAT の直後と PCR 基準の間隔 (NIT 10 秒 / SDT 2 秒 / EIT 1 秒 / TOT 5 秒) で差し込む。
   - NIT (0x40): network_name に TS 名、TS ループに TS_information 記述子の写しと service_list。
   - SDT (0x42): サービスごとに SIT の service 記述子をそのまま。EIT p/f フラグ 1、running_status 4。
   - EIT[p/f] (0x4E): present は event_id・開始時刻・長さ + SIT の番組系記述子 (バイト単位の写し)。following は空 (SIT に情報がないため、制限として明示)。番組が変わると version を進める。
   - TOT (0x73): SIT の JST_time を基準に、PCR の経過で進めた時刻。local_time_offset 記述子は JPN・オフセット 0。
   - 記述子は再符号化せずバイト単位で写すため、ARIB 文字列の化けや欠落が起きない設計。
6. 出力は `<名前>.partial` に書いて完了後にリネーム。入力は開くだけで変更しない。出力が入力と同一パスになる場合は拒否し、既存出力は `--overwrite` なしではスキップする。

## 3. 静的レビュー

### 3.1 良い点

- **入力の保全**: 入力を変更しない、`.partial` 経由のリネーム、同一パス上書きの拒否、既存出力のスキップが揃っている (本リポジトリのファイル操作の流儀とも合う)。
- **SIT は CRC 一致時のみ解析**するので、壊れたセクションで誤った表を作らない。
- **冪等性の設計が明示的**: 既存表 PID の除去 + PAT 書き換えの冪等性で「変換済みの再変換 = 同じバイト列」を構造で担保している (§5 で実測も一致)。
- **制限の正直な明示**: EIT following が空、EIT[schedule] を作らない、録画先頭で前の番組が出ることがある、CS 未検証、を PR 本文・README・docs/53 のすべてで隠さず書いている。
- **manifest の意味を守る判断**: docs/53 §3.3 で「manifest と SHA-256 は nasne から受け取ったバイト列の記録であり、変換版を混ぜると検証の意味が変わる」として救出本体への組み込みを見送った判断は、本ツールの設計原則 (docs/49・50) と一致する。

### 3.2 確認して問題なしとした点

- **合成セクションの第 2 バイト (0xF0 系)**: 一見すると private_indicator の誤りに見えるが、SI 表 (NIT / SDT / EIT) ではこのビット位置は reserved_future_use で 1 が正しい形であり、レコーダ自身が出す SIT の第 2 バイトも 0xF1 / 0xF2 (同パターン) だった。PAT は PSI なので 0xB0 (元の PAT も 0xB0 で、書き換え後も維持)。TOT の 0x70 も ssi=0 の SI 形として整合する。実測 (§5) でも全セクションの CRC が一致し、ffprobe が SDT を読んだ。
- **CRC32 (MPEG) の実装・セクション長の計算・連続性カウンタの管理**は標準どおり。Packetizer の CC は PID ごとに進み、§5 の走査でも抜け・重複なし。
- **event_group 記述子 (0xD6) が EIT にも写る**が、EIT でも有効な記述子であり実害はない。
- **資格情報・鍵**: ts_fix.py の import は argparse / sys / pathlib のみ。ネットワークにも credentials.env にも触れない。入力は復号済みの TS ファイルだけであり、鍵の消費者は pydtcpip のみという原則に影響しない。

### 3.3 軽微な指摘 (いずれも取り込みの阻害要因ではない)

1. **SIT のない 188 バイト TS を入れた場合**: PID 0x10〜0x14 が捨てられたまま再生成されず、出力から NIT / SDT / EIT / TOT が静かに消える。想定入力 (救出物とその変換済み) の範囲外だが、`sit=0` のときに警告を出すと親切 (統計は既に表示される)。
2. **同期バイトの合わないパケットを黙って読み飛ばす** (`pkt[0] != 0x47` で continue)。壊れた入力で出力が短くなってもエラーにならない。救出物では起きないが、件数の表示があると切り分けが楽になる。
3. **変換失敗時に `.partial` が出力先に残る**。次回の実行は既存出力チェックが `.partial` ではなく本出力を見るため実害は小さいが、後始末はあってもよい。
4. **NIT の network_name に TS 名を入れている**。意味としては TS の名前でありネットワーク名ではないが、表示上の実害はほぼない (地上波では両者は近い)。
5. **PCR を見る前に PAT が来る間は表の差し込み間隔が効かない** (PCR 未確定時は常に due)。実測の追加パケット数は想定間隔と整合しており、実害は確認できなかった。

## 5. 実データでの検証 (当方)

実機 (公式 FW の nasne) は 200 件ためキャンペーン中だが、本検証はディスク上の既存サンプルだけで完結し、**実機へのアクセス・コピーの消費は一切していない**。

### 5.1 素材

torne mobile HB の字幕検証 (2026-11-17) で pydtcpip `stream` により取得した実救出 TS を再利用した (いずれも地上波・NHK Eテレ、192 バイト部分 TS)。

### 5.2 結果

変換は 2 件合計 4.5 秒 (marnux)。作業場所は `SonyNasne-DTCP.work/2026-11-20-pr2-review/` (検証スクリプト `validate_fixed.py` / `kept_packets.py` を保存)。

- **構造 (独自検証スクリプトで全パケット・全セクション走査)**: 両件とも、サイズが 188 の倍数、全パケット同期一致、PAT のネットワーク PID = 0x0010、PAT / NIT / SDT / EIT / TOT の全セクション CRC 一致 (不一致 0)、合成 PID の連続性カウンタの抜け・重複 0、4 表すべて出現。セクション数 (x3 / DR): NIT 30 / 12、SDT 140 / 55、EIT 546 / 210、TOT 56 / 22。
- **番組情報の実在**: SDT の service 記述子に事業者名 (NHK) と ARIB 符号のサービス名、EIT の short_event に `jpn` + ARIB 符号の番組名が入っていることを生バイトで確認した。
- **主流ツールでの読み出し**: ffprobe で、変換前は付かなかった `service_name` が変換版では読めた (値は ARIB 符号のまま表示される。ARIB の復号は ariblib 等の担当で、貢献者はそちらで番組名まで確認済み)。
- **保持パケットのバイト同一性**: PAT と合成表 PID を除く全 PID (映像・音声・字幕・データ・PMT・SIT・PCR) について、入力 (TTS を落とした列) と出力のパケット列が**完全一致** (両件とも全 PID で identical)。「映像・音声に触れない」が実測でも成立。
- **冪等性・決定性**: 変換版の再変換、元ファイルの再変換とも、変換版初回の SHA-256 と完全一致 (rec_dr.ts 変換版: `1bf64c4b7bef364a9b840761f5f3832313fd5bb5e997d28e1702d4ad1959ae70`、rec_x3_fushigi.ts 変換版: `ceb93e748df5d22c6238b5e3b7804d8b6405442c391ab45c12ac0ff8453df8aa`)。
- **入力の不変**: 変換前後で入力 2 件の SHA-256 は一致 (変更されていない)。
- 変換版の出力ファイル自体は検証後に作業場所から削除した (決定性が確認できており、同じ入力からいつでも再生成できる)。

貢献者の検証 (CUHJ-15004、地上波 + BS) と当方の検証 (SIE 機由来の素材、地上波) で、機種・放送波の相互補完が取れた。CS は双方とも未検証。

## 6. 統合方針の提案 (選択式)

本人の方針: **救出ツールで、従来方式 (救出 TS をそのまま保存) と PR #2 の方式 (番組情報の読める TS へ変換) を選べるようにする。**

### 6.1 前提の整理

- ts_fix は救出の代替ではなく後処理なので、「選択」は **fetch の成功後に変換も行うか** という形になる。従来方式は現行の挙動そのもの (変換しない) で、後方互換は自然に保てる。
- 貢献者自身が docs/53 §3.3 で「救出と変換は分ける」判断をしており、PR をそのまま取り込むことはその設計と衝突しない。選択の UI はツールの利用形態の問題として、こちら側の後続変更で足すのが筋である。

### 6.2 推奨手順 (2 段階)

1. **PR #2 をそのまま取り込む**: 独立ツールとして ts_fix.py が使えるようになる。救出経路・資格情報・manifest に無変更で、リスクが最も小さい。§3.3 の軽微な指摘は、必要なら取り込み後の改善として扱う (投稿者へ修正依頼を出すかどうかは本人の判断)。
2. **選択の配線を後続の変更で追加する** (当方作業):
   - CLI: `rescue.py fetch` / `fetch-all` に `--fix` オプション。成功した fetch の直後に変換し、`out/fixed/<ファイル名>` へ出す (独立ツールの既定配置と同じ)。変換の失敗は救出の失敗とは分けて報告し、救出結果 (manifest) には影響させない。
   - GUI: fetch ボタンの近くにチェックボックス「番組情報を読める TS に変換する (fixed/ に出力)」。**既定はオフ** (従来方式) とし、利用者が選んだときだけ変換する。
   - 実装の置き方: ts_fix.py の `Converter` を同一フォルダから import して使う (標準ライブラリのみで追加依存なし)。サブプロセスでもよいが、進捗表示とエラー伝播は import の方が素直。
   - 記録: manifest は従来どおり変換前のファイルの記録のまま変えない。変換を行った場合はサイドカー `.ts.json` に変換版の所在と SHA-256 を追記する案が、検証可能性を保ったまま所在を失わない (要否は実装時に本人が決める)。
   - fetch-all で大量に変換する場合は所要時間が 1 件あたり数秒〜十数秒増える (docs/53 §6.4 の実測では 1〜2 GB で 5〜10 秒)。GUI では進捗表示の対象に含める。

### 6.3 PR をそのまま取り込まない場合との比較

- 投稿者に「選択式への作り替え」を依頼する形: 投稿者の設計判断 (§3.3) と正面からぶつかり、往復も増える。得るものは少なく、推奨しない。
- 配線を先に作ってから PR を取り込む形: ts_fix.py が main に無い間は配線の実装・検証が宙に浮く。順序として不自然で、推奨しない。

## 7. 結論

- PR #2 は、救出物の形式という実在の欠落 (番組情報が一般ツールから読めない) に対する、範囲の正しい後処理の追加である。静的レビューで阻害要因はなく、当方の実データ検証でも構造・同一性・冪等性がすべて成立した。
- 取り込みは「そのまま取り込み → 選択の配線を後続で追加」の 2 段階を提案する。マージの可否と時期は本人の判断。
